# Ручная SGF-разметка/комментарии — дизайн-спек

## Контекст

Возможность зафиксирована в backlog `task_plan.md` (пункт «Ручная SGF-разметка/комментарии с сохранением», поднята пользователем 2026-08-05) и явно отложена «до после» среза Фазы 2 (`weak_group`), который уже завершён, смёржен в `main` и запушен. Пользователь явно попросил начать эту фичу 2026-08-06.

Не привязано к LLM и не является одним из 6 пронумерованных пунктов roadmap `docs/ARCHITECTURE.md` — это расширение уже реализованной Фазы 1 (viewer → editor). `docs/ARCHITECTURE.md` (строка 38) только вскользь упоминает «Board renderer / SGF viewer-editor... разметка» без деталей — эта фича формализует то, что раньше было лишь намерением.

Сейчас Фаза 1 читает партию из SGF, но: (а) не отображает существующие `C[]`/`LB[]`/`TR[]`/`SQ[]`/`CR[]`/`MA[]`, (б) не даёт добавлять их, (в) не умеет сохранять/экспортировать SGF вообще — только drag&drop чтение через File API в рендерере, без записи файлов на диск.

## Scope

**В скоуп:**
- Разметка существующих узлов дерева (буквенно-цифровые метки `LB`, фигуры `TR`/`SQ`/`CR`/`MA`) и текстовый комментарий узла (`C[]`).
- Чтение и отображение уже существующей разметки/комментариев при открытии стороннего SGF.
- Сохранение разметки обратно в SGF-файл (перезапись исходного + «Сохранить как»).

**Вне скоупа (явное решение пользователя):**
- Редактирование дерева ходов (добавление/удаление веток, вставка ходов не из партии) — дерево остаётся таким, как распарсено из SGF, меняются только `data`-свойства существующих узлов.
- Undo/redo для действий разметки.
- Всё, что связано с LLM (это отдельная, уже реализованная возможность — Фаза 2).

## Модель данных и сохранение

Дерево партии (`GameTree` из `@sabaki/immutable-gametree`) остаётся единственным источником истины — разметка и комментарий хранятся прямо как SGF-свойства узла, не в параллельном сторе:

- Расстановка/снятие фигуры или метки → `currentTree.value = currentTree.value.mutate(draft => { draft.addToProperty(nodeId, 'TR', vertexSgfCoord) })` (аналогично `removeFromProperty`, `updateProperty` для `LB`/`C`).
- Сохранение в файл — сериализация всего дерева: `sgf.stringify(tree.root)` (пакет `@sabaki/sgf` уже используется для парсинга; `stringify` принимает ту же форму `{data, children}`, что и `tree.root`, — специального адаптера не нужно).
- Путь исходного файла запоминается при загрузке через `webUtils.getPathForFile(file)` (Electron 32+ API; `file.path` устарел) — хранится в новом сигнале `currentFilePath: Signal<string | null>` рядом с `currentTree` в `appState.ts`.
- Новый сигнал `isDirty: Signal<boolean>` — `true` после любой мутации дерева (разметка, метка, комментарий), `false` после успешного сохранения и сразу после загрузки нового файла. Используется для индикатора несохранённых изменений в UI и для предупреждения при закрытии окна.

**Сохранение — новый IPC-контракт main↔renderer** (аналог уже существующего `backend:get-connection`):
- `file:save(path: string, content: string) -> void` — пишет через `fs.writeFile`, бросает при ошибке (например, файл только для чтения) — сообщение пробрасывается в renderer и показывается баннером ошибки в существующем стиле (`app-shell__banner app-shell__banner--error`).
- `file:save-as(defaultPath: string | undefined, content: string) -> { path: string } | { canceled: true }` — открывает `dialog.showSaveDialog` с фильтром `*.sgf`, пишет выбранный файл, возвращает новый путь (renderer обновляет `currentFilePath`).
- «Сохранить» (если `currentFilePath` известен) вызывает `file:save`; если файл был открыт способом, для которого путь получить не удалось (гипотетически — сейчас единственный способ загрузки, drag&drop, всегда даёт путь через `webUtils`), либо путь ещё не установлен — вызывает `file:save-as`.
- Предупреждение о несохранённых изменениях при закрытии окна: обработчик `will-close` в `main/index.ts` проверяет `isDirty` (renderer сообщает текущее состояние через тот же IPC-мост, аналогично `backend:get-connection`) и показывает `dialog.showMessageBox` с выбором «Сохранить и закрыть / Закрыть без сохранения / Отмена» — нативный диалог, без кастомного UI.

## Взаимодействие с доской

**Тулбар** — рядом с доской, там же, где сейчас чекбоксы «Владение (heatmap)» / «Предлагаемые ходы» в `BoardView.tsx`. Инструменты (взаимоисключающий выбор, как радио-группа):

- Треугольник (`TR`), Квадрат (`SQ`), Круг (`CR`), Крестик (`MA`) — фигуры без текста.
- Метка (`LB`) — при выборе инструмента и до клика показывает следующий по порядку буквенно-цифровой символ (автоинкремент: A, B, C... или 1, 2, 3... — переключатель букв/цифр в самом инструменте), с возможностью вручную поправить текст в поле рядом с кнопкой перед постановкой на доску.
- Ластик — клик по точке удаляет любую разметку в этой точке (фигуру или метку), независимо от типа.

Клик по вершине доски (новый `onVertexClick` на `BoundedGoban` — сейчас там только `onVertexPointerEnter`/`Leave` для hover, конфликтов с существующей логикой нет) применяет выбранный инструмент к этой точке через мутацию дерева.

**Приоритет и видимость:**
- Пользовательская разметка видна на доске всегда, независимо от активной вкладки панели анализа («KataGo»/«LLM»/«Разметка») — она принадлежит позиции, а не конкретному анализу.
- Коллизия с PV-номерами KataGo (уже рисуются через `markerMap` в `BoardView.tsx`): если в вершине есть пользовательская разметка, она перекрывает PV-метку в той же точке. Существующая функция `buildMarkerMap` в `BoardView.tsx` расширяется: сначала накладывается слой пользовательской разметки из `node.data` текущего узла (фигуры/метки), затем поверх — последний ход и PV-кандидаты, но **пропуская** вершины, уже занятые пользовательской разметкой.

**Чтение чужой разметки** — уже «бесплатно»: `sgfLoader.ts` парсит все SGF-свойства узла в `node.data` независимо от того, знает ли о них остальной код. Нужен только рендер: та же расширенная `buildMarkerMap` читает `node.data.TR`/`SQ`/`CR`/`MA`/`LB` текущего узла при отображении позиции, конвертируя SGF-координаты в vertex так же, как уже делает `boardPosition.ts` (`sgfCoordToVertex`).

## Комментарий узла

Третья вкладка «Разметка» в `AnalysisPanel.tsx` (рядом с уже существующими «KataGo»/«LLM») содержит `<textarea>`, привязанный к `C[]`-свойству текущего узла (`currentNodeId`):
- При переключении узла — поле перечитывает `node.data.C?.[0] ?? ''`.
- Изменение сохраняется в дерево через `tree.mutate(draft => draft.updateProperty(nodeId, 'C', [text]))` по `onBlur` или debounce (не на каждое нажатие клавиши — иначе на каждый символ создаётся новая иммутабельная версия дерева).

## Ошибки

- Ошибка чтения файла при загрузке — уже покрыто существующим `sgfError`-баннером (`App.tsx`), без изменений.
- Ошибка записи при сохранении (нет прав, диск занят и т.п.) — новый баннер `app-shell__banner--error` с сообщением из перехваченного исключения `fs.writeFile`, в том же визуальном стиле, что и существующие баннеры ошибок анализа.
- Отмена в диалоге «Сохранить как» — не ошибка, тихо ничего не меняет (`isDirty` остаётся `true`).

## Тестирование

В стиле уже существующих тестов проекта:
- **Frontend, юнит/компонентные (Vitest+jsdom)**: расширенная `buildMarkerMap` — тест на слияние пользовательской разметки + PV-меток с проверкой приоритета; тулбар — выбор инструмента, клик по вершине вызывает ожидаемую мутацию дерева; текстовое поле комментария — привязка к текущему узлу, debounce/onBlur-сохранение; сериализация — тест, что `sgf.stringify` на дереве после нескольких мутаций даёт ожидаемый SGF-текст (round-trip: parse → mutate → stringify → parse снова → сравнить свойства узлов).
- **IPC-клиент**: `saveFile()`/`saveFileAs()` в `ipc/client.ts` (или отдельном модуле) — мок `window.baduk`, аналог существующих тестов `explainPosition`/`analyzePosition` в `client.test.ts`.
- **Main-process**: обработчики `file:save`/`file:save-as`/`will-close` — мок `fs`/`dialog` из `electron`, проверка вызова с ожидаемыми аргументами и обработки ошибок/отмены.

## Критерии готовности

- Открыт SGF с существующей разметкой/комментариями сторонней программы — разметка видна на доске, комментарии — во вкладке «Разметка».
- Пользователь ставит фигуру/метку через тулбар, вводит комментарий — визуально отражается немедленно, `isDirty` становится `true`.
- «Сохранить» перезаписывает исходный файл; открытие сохранённого файла заново показывает те же разметку и комментарии.
- «Сохранить как» создаёт новый файл, не трогая исходный.
- Попытка закрыть окно с несохранёнными изменениями показывает предупреждение.
