# Архитектура: Baduk Assistant — ИИ-ассистент по анализу партий в Го

## Контекст

Репозиторий `baduk_assistant` сейчас пуст (только README и LICENSE) — это greenfield-проект. Идея: настольное приложение, которое позволяет просматривать партии в Го (SGF), анализировать их движком KataGo с выбором/настройкой моделей, а затем LLM с опорой на RAG-базу знаний объясняет ход анализа рационально и педагогически — как тренер объясняет ученику кю-уровня, а не как чёрный ящик. Дополнительно — модуль "паспорт игрока", который аккумулирует статистику по партиям и показывает сильные/слабые стороны игрока во времени. Требование к архитектуре — плагинность, чтобы приложение дорабатывалось модулями без изменения ядра.

Пользователь явно попросил: сейчас нужен **только полный архитектурный дизайн**, без перехода к разработке. Реализация в дальнейшем будет поэтапной (MVP-first), но сама архитектура проектируется целиком заранее, чтобы поэтапные фазы не требовали переписывания ядра.

Ключевые решения ниже приняты пользователем в ходе обсуждения:
- LLM-подход: **гибрид с выбором в настройках** (облачный API вроде Claude/OpenAI и локальные модели через Ollama, переключаемо).
- RAG-контент: **начать с открытых источников** (go proverbs, joseki-словари, tsumego/life-and-death коллекции, Sensei's Library и т.п.).
- Подход к плану: **поэтапный MVP-roadmap**, а не разовая реализация всего.
- Выбор "ядра": проведён сравнительный анализ опенсорсных решений (см. ниже), а не слепой форк одного из них.

## Сравнение открытых движков/GUI и рекомендация по стеку

| **Sabaki** | Electron/JS+Preact | MIT-подобная | Win/Mac/Linux из коробки | Зрелый, много edge-cases решено | GTP (не Analysis Engine нативно) | Веб-стек удобен для UI-плагинов, но заточен под "один GTP-процесс на партию", не под batch Analysis Engine. LLM/RAG на JS менее зрелый |

| **q5Go** | C++/Qt5 | GPL-2.0-or-later | Да | Полнофункциональный (IGS, БД партий, паттерн-серч) | GTP + KataGo | Copyleft ограничивает лицензионную гибкость. C++/Qt почти несовместим с Python LLM/RAG tooling |
| **Lizzie (форки)** | Java | Разное, устарело | Да | Слабый/забагованный по отзывам сообщества | GTP, live-анализ | Не рекомендуется — считается устаревшим самим сообществом |
| **Ogatak** | Electron/JS | Открытая, легковесная | Из коробки | Достаточный, заточен именно под Analysis Engine | Analysis Engine нативно | Хороший референс IPC-архитектуры с Analysis Engine, но тонкий однофункциональный вьюер без слоя данных/плагинов/LLM |
| **GoReviewPartner** | Python-скрипт | Открытая | Не GUI | Нет GUI | Батч-интеграция была нетривиальной | Не основа для GUI, но подтверждает Python как типичный язык для batch-review поверх KataGo |

**Рекомендация: не форкать ни один проект целиком.** Собрать продукт из двух явно разделённых слоёв, каждый — лучший в своей нише:

- **Frontend/UI: Electron + TypeScript**, вдохновляясь Sabaki и особенно Ogatak (самый близкий референс — лёгкий клиент именно вокруг Analysis Engine). Переиспользовать готовый open-source компонент доски — **Shudan** (Preact, из экосистемы Sabaki) или **WGo.js** — вместо написания рендеринга доски с нуля.
- **UI-фреймворк — Preact для всего фронтенда**, не только для доски. Решение принято сравнением, а не по умолчанию: Shudan написан напрямую на Preact API, поэтому Preact даёт нулевую цену интеграции (тот же reconciler/VDOM, реальная композиция), тогда как React/Svelte/Vue потребовали бы либо `preact/compat`-алиаса (что фактически и есть выбор Preact, только под другим именем), либо императивного двойного монтирования Shudan как отдельного рантайма внутри чужого дерева компонентов. Дополнительно: самый лёгкий рантайм (~4KB); через `preact/compat` всё равно доступна экосистема React (включая shadcn/Radix-компоненты, если понадобятся) на одном рантайме, а не ценой второго; `@preact/signals` хорошо ложится на потоковый характер обновлений приложения (WebSocket-прогресс KataGo-анализа, токены LLM-объяснения, live winrate/PV). Оговорка: `preact/compat` не покрывает 100% API React (Suspense-for-data-fetching, часть `react-dom/client`) — конкретные React-only библиотеки проверяются точечно в Фазе 1, совместимость не считается гарантированной по умолчанию.
- **Backend/core-service: Python.** LangChain/LlamaIndex, embedding-модели, локальные LLM через Ollama, RAG-тулинг (chunking, retrievers, reranking) — де-факто Python-first экосистема. Повторение этого на Node/TS означало бы либо отставание в возможностях, либо самостоятельное написание RAG-инфраструктуры.
- Qt/C++ и Kivy отклонены как основа GUI — несовместимы с веб-based plugin host на фронтенде и с Python LLM/RAG-экосистемой на бэкенде. q5Go отдельно отклонён по лицензии (GPL ограничивает будущую гибкость плагинного API).

Итог: **гибридная two-process архитектура — Electron/TS frontend + Python backend-сервис**, связанные локальным IPC. Плата — два рантайма в одном десктоп-приложении, но это прямо соответствует требованиям (плагины на обеих сторонах, гибридный LLM, гибкая настройка KataGo-профилей) и не требует переписывания ядра при росте.

## Общая архитектура системы

### Frontend (Electron + TypeScript)
- **Board renderer / SGF viewer-editor** на базе Shudan/WGo.js — навигация по дереву вариаций, разметка, drag&drop загрузка SGF.
- **Analysis overlay panels** — winrate-график по ходам, ownership heatmap, PV-стрелки, score lead (данные от backend, рендер на фронте).
- **Settings UI** — KataGo-профили (модели+конфиги), выбор LLM-провайдера и параметров, вкл/выкл RAG-источников, plugin manager UI.
- **LLM explanation panel** — педагогические объяснения (текст + ссылки на цитируемые RAG-источники + подсветка соответствующих ходов).
- **Player Passport UI** — дашборд профиля игрока.
- **Frontend Plugin Host** — реестр точек расширения для сторонних UI-панелей/визуализаций.
- Frontend тонкий, презентационный — вся бизнес-логика анализа и LLM-оркестрация на backend.

### Backend (Python core-service)
- **Engine Manager** — жизненный цикл процессов KataGo Analysis Engine: запуск/остановка по требованию, пул процессов под разные модели/конфиги, маршрутизация JSON stdin/stdout, restart on crash.
- **LLM Orchestrator** — провайдер-абстракция (`LLMProvider.complete(messages, tools) -> response`) с реализациями Claude API / OpenAI API / Ollama, переключаемо в конфиге без перезапуска.
- **Feature Extraction layer** — детерминированный (не-LLM) слой, превращающий сырые числа KataGo в структурированные находки.
- **RAG subsystem** — ingestion pipeline (открытые источники → чанкинг → эмбеддинг → embedded vector store) + retriever как tool для LLM.
- **Player Passport analytics engine** — агрегация находок по всем партиям в профиль, инкрементальное обновление.
- **Game/SGF database** — метаданные партий, индекс библиотеки SGF.
- **Analysis cache** — кэш результатов KataGo по `(position_hash, model_id, config_id)`.
- **Backend Plugin Host** — новые LLM-провайдеры, RAG-источники, метрики паспорта, постобработчики анализа.

### Взаимодействие Frontend ↔ Backend
Backend — **sidecar-процесс**, запускаемый Electron main-процессом при старте. Локальный **HTTP + WebSocket API на `127.0.0.1:<динамический порт>`**, с токеном аутентификации через env/аргумент запуска (исключает доступ сторонних процессов):
- HTTP REST — CRUD над играми, профилями, настройками, паспортом.
- WebSocket — потоковый прогресс анализа KataGo, потоковая генерация LLM-объяснения (token streaming).

Разделение процессов даёт устойчивость (падение долгого KataGo-анализа не роняет UI) и позволяет в будущем вынести backend в standalone-сервис без переписывания.

### Упаковка
- **Windows (сейчас)**: единый инсталлятор (electron-builder), Python backend — embedded/frozen интерпретатор (PyInstaller) как sidecar-бинарник внутри ресурсов Electron-приложения. KataGo-бинарник и модели — отдельные артефакты, которые пользователь скачивает/указывает сам (не встраиваются из-за размера и GPU-специфичности сборок).
- **Кросс-платформенность (будущее)**: electron-builder и PyInstaller поддерживают Mac/Linux "из коробки" при условии, что backend не использует Windows-специфичных путей/API (`pathlib`, кроссплатформенный `subprocess`, user-data-dir через `platformdirs`). Это архитектурное требование действует **с самого начала**, чтобы фаза 6 (кросс-платформенная валидация) была полировкой, а не переписыванием.

## LLM + RAG reasoning pipeline: кейс "слабая группа → RAG → объяснение"

Принцип: **KataGo — источник истины по оценке позиции, LLM — интерпретатор, RAG — источник объяснительных знаний.** LLM никогда не переоценивает позицию против чисел движка.

**1. Сигналы от KataGo Analysis Engine** (запрос с `includeOwnership`, `maxVisits`): `moveInfos[]` (winrate, scoreLead, scoreStdev, visits, pv, prior), `rootInfo` (агрегаты по текущей позиции), `ownership[]` (per-intersection контроль от -1 до 1). По ходам партии собирается последовательность дельт winrate/scoreLead — стандартная метрика "потери очков за ход".

**2. Детерминированный feature-extraction слой (не-LLM) — формализованные алгоритмы, не расплывчатые эвристики.**

Каждый детектор — чистая функция от чисел KataGo и состояния доски, с явными формулами и конфигурируемыми (не зашитыми в код) параметрами:

- **Идентификация групп и дыхания (liberties)** — детерминированно, без эвристик: union-find по соседним камням одного цвета даёт группы; число дыханий — прямой подсчёт пустых соседних точек. Это не требует KataGo вообще, только состояние доски.
- **Достоверность владения (ownership certainty)** — по `ownership[]` (доступен при `includeOwnership: true`, надёжен только от `min_reliable_visits` посещений — например, 500; ниже этого порога находки на основе ownership помечаются `confidence: low` или не создаются вовсе):
  - `own_certainty(G) = mean(|ownership[p]|` по всем точкам группы `G)` — 1.0 = позиция вокруг группы решена, 0 = максимально спорная.
  - `boundary_certainty(G) = mean(|ownership[p]|` по пустым точкам в радиусе 1 линии от `G)`.
- **Концентрация топ-вариантов (PV focus)** — по top-K `moveInfos` текущего узла (K конфигурируем, напр. 5): `pv_focus(G) = доля этих K ходов, чьи координаты лежат в пределах расстояния D от любого камня G` (D конфигурируем, напр. 2 клетки). Высокое значение = сильнейшие кандидат-ходы движка сосредоточены именно вокруг этой группы — то есть это "живой" вопрос в позиции прямо сейчас.
  - Композитная оценка: `weak_score(G) = w1·(1 − own_certainty(G)) + w2·(1 − boundary_certainty(G)) + w3·pv_focus(G) − w4·(liberties(G) / max_liberties_norm)`, веса `w1..w4` — из версионированного конфига (см. ниже), результат нормализован в `[0,1]`.
  - Находка `weak_group` создаётся при `weak_score(G) > threshold_weak`; `confidence = min(visits / reliable_visits_threshold, 1.0)`; `severity` — бакет от `weak_score` по конфигурируемым границам (напр. `<0.7` low, `<0.85` medium, иначе high).
- **Mistake detector**: `Δ = scoreLead(лучший ход по PV) − scoreLead(сыгранный ход)`, отдельно в очках и в % winrate. Стадия игры вычисляется детерминированно от позиции, а не "на глаз": `stage = opening`, если `move_number ≤ board_area · k_open`; `endgame`, если `empty_points_left ≤ board_area · k_end`; иначе `middlegame` (`k_open`, `k_end` — конфигурируемые доли, напр. 0.12 и 0.15). Порог на `Δ` берётся из таблицы по стадии (напр. `{opening: 3.0, middlegame: 2.0, endgame: 1.0}` очка) — тоже из конфига, не хардкод "шире/уже".
- **Opening loss detector**: накопленная `Δ` за первые N ходов (N конфигурируем) сверх табличного порога.
- Каждая находка несёт явные поля `confidence` (0–1, из числа посещений/устойчивости сигнала) и `severity` (low/medium/high) — это не декоративные метки, а обязательные входы для LLM-промпта: находки с `confidence` ниже настраиваемого минимума в объяснение вообще не попадают; для `medium` LLM обязана использовать hedging-язык ("похоже, эта группа...", "вероятно"), для `high` — уверенные формулировки. Так численная неопределённость детектора явно транслируется в тон объяснения, а не теряется на пути к LLM.

Почему детерминированно и формализовано именно так: (а) воспроизводимость — одинаковый вход всегда даёт одинаковую классификацию (критично для Player Passport — стабильная таксономия во времени); (б) LLM ненадёжна в точной числовой пороговой логике по сырым массивам; (в) детектор гарантированно не "спорит" с движком, будучи строгой функцией его чисел; (г) явные формулы и конфигурируемые параметры — а не текстовые эвристики — это то, что вообще делает калибровку (см. ниже) возможной.

**2а. Калибровка и итеративная донастройка детекторов.**

Это первоклассный архитектурный компонент, а не пост-фактум доработка — существует с Фазы 2 (когда feature-extraction впервые появляется), живёт в `backend/feature_extraction/calibration/`:

- **Версионированный конфиг**: все параметры детекторов (`w1..w4`, `threshold_weak`, `k_open`, `k_end`, таблица порогов по стадиям, `min_reliable_visits`, границы `severity`) — в файле `detector_config.v{N}.json`. Донастройка = выпуск новой версии конфига, а не правка кода детекторов или промптов LLM.
- **Backtesting harness** (офлайн-инструмент разработчика, часть backend, не пользовательская фича в MVP): прогоняет кандидат-конфиг против размеченного validation-набора и считает precision/recall/F1 по каждому типу находки, прежде чем новая версия конфига становится дефолтной.
- **Источники ground truth** (готового экспертно размеченного корпуса нет, поэтому — три сходящихся источника, не один):
  1. **Self-consistency proxy** (полностью автоматизируемый, не требует людей): позиция, помеченная находкой на быстром проходе (малый visits budget), переанализируется с намного большим visits budget; если находка подтверждается на глубоком проходе — позитивный label, если нет — негативный/шум. Прямо ловит failure mode "быстрая эвристика видит то, чего не подтверждает более глубокий взгляд".
  2. **Открытые tsumego/life-and-death коллекции** (те же, что заложены под RAG в Фазе 3) — задачи с известным правильным/неправильным решением дают однозначный ground truth именно для `life_and_death`/`weak_group`.
  3. **Обратная связь пользователя**: в UI (Player Passport) пользователь может пометить находку/объяснение LLM как "неточно". Помеченная находка сохраняется со снапшотом позиции и `finding_id` и пополняет размеченный набор для следующих калибровок — растущий во времени источник. Именно поэтому в схеме находок и в Player Passport хранится стабильный `finding_id`, а не просто текст объяснения — чтобы пользовательская коррекция могла точно сослаться на конкретную находку.

**3. Структурированный ввод для LLM + tool-use.** Feature-extraction даёт компактные finding-объекты, например: `{type: "weak_group", move_range: [23,31], stones: [...], ownership_avg: 0.15, winrate_trend: [...], severity: "medium", confidence: 0.82, finding_id: "f_2f9a"}`. LLM получает эти находки + tool:

```
retrieve_knowledge(
  category: "weak_group" | "joseki" | "life_and_death" | "proverb" | "opening_principle" | "tesuji",
  query: string,
  board_context: { stones: [...], move_number: int },  // опционально
  top_k: int
) -> [{ doc_id, title, source, text_snippet, relevance_score }]
```
System prompt инструктирует: находка типа `weak_group` → обязателен вызов `retrieve_knowledge` с соответствующей категорией до формулировки объяснения.

**4. Комбинирование и предотвращение противоречий.** LLM обязана: (а) цитировать конкретные числа из finding-объекта, не выдумывая новые; (б) явно связывать RAG-фрагмент с этими числами; (в) не формулировать собственную оценку позиции — интерпретирует уже данную KataGo, никогда не говорит "на самом деле здесь всё в порядке" вопреки движку. Роль LLM — "что это значит для ученика и что советует теория", а не "что правильно по позиции" (это уже решено движком).

**5. Валидация против галлюцинаций** — две ступени:
- **Structured-output constraint**: LLM возвращает JSON с `claims[]`, каждый claim ссылается на `finding_id` или `doc_id` как источник; финальный текст рендерится шаблонизатором из этой структуры, а не выводится как raw completion.
- **Post-hoc numeric consistency checker** (код, не LLM): парсит числа в финальном тексте, сверяет с исходными finding-объектами; при расхождении — перегенерация с уточняющим промптом ("ты указал X, но исходное значение Y"), после N попыток — fallback на шаблонный ответ без свободной генерации.

## Плагинная архитектура

**Манифест плагина** (`plugin.json` в папке плагина):
```json
{
  "id": "com.example.tsumego-trainer",
  "name": "Tsumego Trainer Panel",
  "version": "1.0.0",
  "apiVersion": "^1.2",
  "type": "frontend-ui | backend-analysis | rag-source | llm-provider | passport-metric",
  "entry": "index.js | plugin.py",
  "permissions": ["read:game-data", "network:external"],
  "dependencies": []
}
```
`apiVersion` резолвится хостом при загрузке (semver-range); несовместимая мажорная версия — плагин отклоняется без падения ядра.

**Frontend-точки расширения**: `registerAnalysisPanel(mount)`, `registerBoardOverlay(renderer)`, `registerSettingsSection(mount)`. Технический контракт зафиксирован как **framework-agnostic, DOM/Custom Element-based** — плагин отдаёт DOM-узел или Custom Element, никогда framework-specific объект (не Preact VNode), независимо от того, на чём написан сам плагин внутри:

```ts
registerAnalysisPanel({
  mount(container: HTMLElement, ctx: PanelContext): (() => void) | void
})
```

Это осознанный выбор, а не нейтральный: связать контракт с Preact (ядро фронтенда) было бы проще технически, но заперло бы всех сторонних авторов плагинов на внутреннем фреймворке и его версии ядра — и было бы несовместимо с уже обещанным sandboxed-режимом ниже (Preact VNode не сериализуется через `postMessage`, только DOM/данные). Рекомендуемый (не обязательный) паттерн для авторов плагинов — Custom Element (`customElements.define(...)`), тогда `mount()` вырождается в `container.appendChild(...)`, с типизированными properties на вход и `CustomEvent`-ами на выход.

Рендер — либо доверенный компонент в общем рантайме, либо песочница (`iframe`/BrowserView + postMessage) для недоверенных сторонних плагинов, по флагу в манифесте. Оба режима — **один и тот же контракт с двумя разными транспортами**, не два разных API: в доверенном режиме properties/events идут напрямую на DOM-узел, в песочном — тот же набор properties/events транслируется через postMessage-мост с шимом внутри iframe. Автор плагина пишет против одной ментальной модели (mount + properties + events); флаг `sandboxed` в манифесте меняет только способ доставки, не сам контракт.

Design-tokens (CSS custom properties, см. «UI/UX-принципы фронтенда») framework-agnostic и наследуются по DOM-дереву автоматически, но не пересекают границу iframe — для sandboxed-плагинов Plugin Host обязан явно прокидывать resolved-токены в iframe при монтировании и при смене темы через тот же postMessage-мост (расширение уже требующегося механизма, не новый).

**Backend-точки расширения** — hookspec-паттерн (аналог `pluggy`, на котором построен pytest): `register_llm_provider`, `register_rag_source`, `register_metric_extractor`, `register_analysis_postprocessor`. Обнаружение — сканирование `plugins/` при старте, регистрация через entry-points с валидацией манифеста.

**Согласование**: единый формат манифеста для обеих сторон; Plugin Manager UI (фронтенд) показывает единый реестр, читая список backend-плагинов через тот же локальный API.

## UI/UX-принципы фронтенда

Проведён дизайн-ревью фронтенда (скилл `ui-ux-pro-max`, приоритетный чек-лист accessibility → touch/interaction → performance → style → layout → typography/color → animation → forms → navigation → charts) применительно к разделу «Frontend» и к плагинной архитектуре выше. Ниже — архитектурные решения и открытые вопросы, а не финальный визуальный дизайн (палитра/типографика — отправная точка для Фазы 1, не токены для копирования в код без проверки).

**UI-фреймворк — решено.** Ядро фронтенда (settings/passport/LLM-panel/plugin-host) — Preact, тем же рантаймом, что и Shudan (обоснование — см. «Frontend/UI: Electron + TypeScript» выше). Плагинные точки расширения при этом остаются framework-agnostic — DOM/Custom Element контракт, не Preact VNode (см. «Плагинная архитектура») — выбор фреймворка ядра и контракт для плагинов сознательно не связаны: первый решает вопрос «на чём пишет ядро», второй — «что обязан отдать плагин», и их совмещение (а не выбор одного вместо другого) — то, что делает сторонние плагины независимыми от внутреннего рефакторинга ядра и совместимыми с уже обещанным sandboxed-режимом.

**Design tokens — обязательный слой, а не деталь реализации.** Поскольку сторонние плагины рендерят свои панели в общем UI (плагинная архитектура выше), они обязаны получать общую тему (CSS custom properties: цвет, spacing-scale, radius-scale, elevation) через Plugin Host, а не хардкодить свою. Без этого контракта Фаза 5 (формализация плагинов) будет ломать уже написанные сторонние панели, вводя тему постфактум.

**Тема — Dark Mode (OLED) по умолчанию для MVP.** Соответствует практике аналогичных инструментов (Ogatak, KaTrain, Lizzie — длинные сессии разбора партий) и подтверждено design-system поиском по продуктовым аналогам (Analytics Dashboard / Real-Time Operations / Productivity Tool). Отправная палитра для Фазы 1:

```
--color-background:   #020617
--color-surface:      #0E1223
--color-primary:      #0F172A
--color-foreground:   #F8FAFC
--color-muted-fg:     #94A3B8
--color-border:       #334155
--color-accent:       #22C55E   /* позитивный winrate/статус */
--color-destructive:  #EF4444   /* потеря очков/ошибка */
```
Контраст этих токенов не проверялся поверх самой доски (чёрные/белые камни + оверлеи) — отдельная задача для UI Фазы 1, т.к. это не общий UI-кейс, а специфика doски Go. Светлая тема — не приоритет MVP, рассмотреть отдельно после Фазы 1, если будет запрос.

**Типографика — пара Fira Code / Fira Sans** ("Dashboard Data" из design-system поиска): Fira Code — для чисел и координат (winrate, scoreLead, visits, PV, паспорт-метрики), Fira Sans — для педагогической прозы LLM-панели. Один шрифтовой вендор снижает вес бандла.

**Ownership heatmap** — cool→hot (blue→red) градиент, обязательно с числовым значением по hover/клику и легендой со шкалой делений; голый цветовой heatmap без pattern/numeric-фолбэка не проходит accessibility (нечитаем для дальтоников) — это должно быть частью контракта `registerBoardOverlay`, а не опциональной доработкой конкретной реализации.

**Winrate/score-график** — line chart (подтверждено); при нескольких сериях (сравнение профилей/моделей KataGo на одном графике) различать серии стилем линии (solid/dashed/dotted), не только цветом; предусмотреть переключаемую табличную альтернативу по ходам для screen-reader-доступности.

**Player Passport dashboard** — стиль Drill-Down Analytics + Comparative: тренд ошибок по времени → line/area chart; сравнение категорий таксономии (`weak_group`, `opening_loss`, L&D и т.д.) → bar chart, не pie — таксономия расширяется плагинами (`register_metric_extractor`), число категорий гарантированно превысит порог, до которого pie ещё читаем.

**Клавиатурная навигация — архитектурное требование, не деталь реализации.** Основной рабочий процесс (навигация по дереву вариаций, переключение панелей) должен быть полностью доступен с клавиатуры без переопределения системных сочетаний — дешевле заложить в IPC/UI-контракт сейчас, чем добавлять поверх готового рендера доски в Фазе 1.

**Settings UI** — прогрессивное раскрытие сложности: core-разделы (KataGo-профили, LLM-провайдер, RAG-источники, Plugin Manager) организуются как отдельные секции через тот же механизм `registerSettingsSection`, что и у плагинов — не одна длинная форма.

**LLM Explanation Panel** — ширина текстовой колонки 60–75 символов (не на всю ширину docked-панели); цитаты RAG (title/source/snippet) не обрезаются без возможности развернуть; подсветка соответствующих ходов на доске должна быть доступна не только по hover, но и по клику/клавиатуре; потоковая генерация (WebSocket) — skeleton/streaming-курсор, не блокирующий спиннер.

## Player Passport

**Таксономия ошибок**, накапливаемая по партиям (соответствует категориям feature-extraction): жизнь-и-смерть (частота несовпадения хода с top-PV в L&D-контексте), слабые группы (частота создания по стадии игры и стороне доски), дебютные потери очков, тактические промахи (при наличии соответствующих детекторов), тренд по времени (динамика за последние M партий, а не только текущий срез).

**Инкрементальное обновление**: при завершении анализа партии находки инкрементально обновляют агрегаты (скользящее среднее/счётчики), т.е. добавление партии — `O(находки этой партии)`, а не пересчёт всей истории. Полный пересчёт — отдельная фоновая операция (например, при добавлении новой категории плагином).

**Хранилище — embedded SQLite**: zero-config, без отдельного серверного процесса (соответствует sidecar-модели), файл БД легко бэкапится копированием, полностью достаточна по производительности для одного пользователя, зрелые Python-биндинги.

## Хранилище данных

```
<user-data-dir>/baduk-assistant/
├── app.db                      # SQLite: метаданные партий, находки, паспорт, plugin registry, настройки
├── sgf_library/                 # исходные SGF-файлы как есть
│   └── <hash-or-id>.sgf
├── analysis_cache/              # кэш KataGo по (position_hash, model_id, config_id)
├── katago/
│   ├── models/                  # .bin.gz модели
│   └── profiles/                # JSON-конфиги профилей (visits/time, rules, board size)
├── rag_store/                   # embedded vector store (персистентная директория)
├── plugins/
│   └── <plugin-id>/plugin.json ...
└── logs/
```

SGF хранится файлами, а не BLOB в БД — пользователи Го привыкли к файловым коллекциям (совместимость с другими программами, шаринг); БД хранит индекс/метаданные + ссылку на путь/хэш.

Кэш анализа индексируется по составному ключу `(hash(position + rules + komi), model_id, config_id)` — позволяет держать результаты нескольких моделей/профилей для одной позиции одновременно.

**Vector store для RAG** — embedded, no-server (Chroma в persistent-режиме, либо LanceDB как более лёгкая альтернатива). Chroma предпочтительна на старте из-за интеграции с LangChain/LlamaIndex.

## Конфигурация KataGo-моделей

- **Модели**: путь к `.bin.gz` указывается через Settings UI (без копирования крупных файлов), запись в `app.db` (`model_id`, `display_name`, `path`, `size_category`).
- **Профили**: JSON-сущность — `model_id` (ссылка), `rules`, `boardSize`, `komi`, `maxVisits`/`maxTime`, `numAnalysisThreads`, GPU-параметры. Несколько профилей на модель (например, быстрый превью vs глубокий анализ).
- **Передача в Analysis Engine**: Engine Manager генерирует `analysis_config.cfg` из шаблона + значений профиля, запускает `katago analysis -model ... -config ...`, дальше JSON-запросы по stdin/stdout (`id`, `moves`, `rules`, `komi`, `boardXSize/YSize`, `analyzeTurns`, `maxVisits`). Смена профиля/модели в UI не требует перезапуска приложения — Engine Manager поднимает/останавливает процессы по требованию.

## Поэтапный MVP-roadmap

Архитектура выше проектируется полностью сразу (hookspecs, provider-абстракция, категории RAG, схема паспорта заложены с фазы 1); формализация и наполнение — поэтапно:

1. **SGF viewer + KataGo-анализ (без LLM).** Electron+TS фронт с доской (Shudan/WGo.js), Python backend с Engine Manager и одним профилем KataGo, визуализация winrate/ownership/PV. SQLite для метаданных и кэша. Реализует полный IPC-контракт frontend↔backend.
2. **LLM-объяснения поверх KataGo (без RAG).** Feature-extraction слой (детекторы + версионированный конфиг + calibration/backtesting harness + self-consistency проверка на глубоком re-scan), LLM Orchestrator с provider-абстракцией (Claude/OpenAI/Ollama), объяснения тоном тренера строго на числах движка с учётом `confidence`/`severity`, без tool-use.
3. **RAG-база знаний.** Ingestion открытых источников (proverbs, joseki-словари, tsumego/L&D-коллекции, Sensei's Library), embedding + vector store, интеграция `retrieve_knowledge` в LLM Orchestrator, механизм валидации из раздела про reasoning pipeline.
4. **Паспорт игрока.** Passport Analytics Engine, инкрементальное обновление, UI-дашборд.
5. **Формализация плагинной системы.** Манифест-формат, semver apiVersion resolution, Plugin Manager UI, документация API для обеих сторон, референсный плагин на каждую из 4 категорий точек расширения.
6. **Кросс-платформенная валидация.** Сборки Mac/Linux (electron-builder + PyInstaller targets), проверка путей/процессов/GPU-конфигов на не-Windows.

## Критические точки для будущей реализации

Репозиторий пуст — "критических файлов" в смысле существующего кода нет. Ниже — файлы, которые должны появиться первыми в Фазе 1 и зафиксируют архитектуру дальше:

- `backend/engine_manager.py` — управление процессами KataGo Analysis Engine, ядро аналитической цепочки.
- `backend/feature_extraction/` — детерминированные детекторы (weak_group, mistake, opening_loss) — на них завязаны и LLM-пайплайн, и Player Passport.
- `backend/feature_extraction/calibration/` — версионированные конфиги детекторов, backtesting harness, хранилище размеченных примеров (self-consistency, tsumego-валидация, пользовательские коррекции).
- `backend/llm/orchestrator.py` (+ `providers/claude.py`, `providers/openai.py`, `providers/ollama.py`) — provider-абстракция LLM.
- `backend/plugin_host/hookspecs.py` — формальные точки расширения backend.
- `frontend/src/ipc/client.ts` — контракт HTTP/WebSocket взаимодействия с backend.
- `shared/schemas/` — общие JSON-схемы (finding-объекты, KataGo profile config, plugin manifest) — единый источник истины для типов на обеих сторонах IPC.

## Проверка (на будущих фазах реализации)

Поскольку сейчас это архитектурный документ без кода, проверка относится к будущим фазам:
- **Фаза 1**: smoke-test IPC — запустить KataGo Analysis Engine через Engine Manager, отправить тестовую позицию, получить и распарсить JSON-ответ (winrate/ownership/PV); открыть SGF во фронтенде и убедиться, что дерево вариаций и доска рендерятся корректно.
- **Фаза 2**: на фиксированных тестовых партиях (fixture SGF + заранее известные находки) проверить, что LLM-объяснение цитирует именно те числа, что в finding-объектах (юнит-тест consistency checker); отдельно прогнать backtesting harness на self-consistency наборе (быстрый vs глубокий re-scan) и убедиться, что precision/recall детекторов выше согласованного минимума перед тем, как конфиг становится дефолтным.
- **Фаза 3**: тест ingestion pipeline на небольшом открытом корпусе — проверить, что `retrieve_knowledge` возвращает релевантные фрагменты для тестовых запросов категории `weak_group`.
- **Фаза 4**: проверить, что добавление тестовой партии с известными находками корректно обновляет агрегаты паспорта инкрементально (сравнить с полным пересчётом).
- **Фаза 5**: загрузить референсный плагин каждого из 4 типов и убедиться, что он появляется в Plugin Manager UI и вызывается хостом.
- **Фаза 6**: собрать и запустить приложение на чистой Mac/Linux VM, пройти основной сценарий (открыть партию → анализ → LLM-объяснение) без Windows-специфичных путей.
